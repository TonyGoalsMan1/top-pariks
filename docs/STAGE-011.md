# STAGE-011 · WordPress Factory

**Решение.** Использовать общий конвейер GitHub Actions для сборки и изолированных тестов, а первым управляемым стендом сделать отдельный WordPress + WooCommerce на Linux VPS. Публиковать на нём проверенный ZIP через SSH и WP-CLI. Хранить зашифрованные копии вне VPS в приватном объектном хранилище. Разрешение на staging выдаётся при подключении сайта. Каждый релиз production и каждая чувствительная операция требуют отдельного решения владельца.

STAGE-011 ограничен аудитом и проектированием. База аудита — `main` на `0c9198097f178e6e1d5b7bcb9a8a29bbc12ec7c4` от 23 ноября 2026 года. Доступ к серверам, настройки окружений, секреты и содержимое БД в этом аудите не проверялись. Изменение в PR — этот документ. Ни один сценарий хостинга на этом этапе не запускается. [База аудита](https://github.com/TonyGoalsMan1/top-pariks/tree/0c9198097f178e6e1d5b7bcb9a8a29bbc12ec7c4)

Preflight подтверждает происхождение артефакта через ожидаемые репозиторий, workflow и SHA, затем проверяет digest, формат пакета и допустимость пути. Операции идемпотентны на пару окружение/digest. Повтор с уже применённым digest сверяет состояние и health. [Артефакты GitHub Actions](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)

## 3. Бэкапы и проверка восстановления

**Предлагаемые цели пилота.** RPO staging ≤24 ч, RTO staging ≤2 ч. Кандидатные цели production — RPO ≤4 ч и RTO ≤4 ч после подтверждения владельцем. RPO измеряется по времени среза последней полной доступной копии. RTO — от объявления инцидента до успешных проверок восстановленного сайта. Для магазина с более строгим RPO отдельно спроектировать восстановление на момент времени и сверку платёжных событий.

1. **Снимок.** Таймер `systemd` на поддерживаемом хосте запускает отдельный backup service. Staging — каждые 12 часов, production после подключения — каждые 3 часа, плюс перед релизом или миграцией. Интервалы оставляют запас на сбор, доставку и проверку. Предупреждение о просрочке — до достижения RPO. Сбор использует блокировку сайта, общую с публикацией. Для согласования БД и файлов использовать короткое окно запрета записи в приложении и остановки фоновых writers на время снятия файлового среза и SQL-снимка. В пилоте измерить длительность окна. Для production с активными заказами отдельно утвердить согласованный механизм снимка и политику ограничения записи. Для InnoDB использовать `mariadb-dump` с консистентной транзакцией, проверить отсутствие параллельных DDL. Для нетранзакционных таблиц нужен отдельный подтверждённый способ консистентного экспорта. Любая ошибка отменяет отметку о готовности. [Документация MariaDB](https://mariadb.com/kb/en/mariadb-dump/)
2. **Состав.** Снять полную выделенную БД WordPress с таблицами плагинов, WooCommerce и Action Scheduler. Учесть текущий режим HPOS, классические таблицы заказов и состояние синхронизации. Включить `wp-content/uploads`, темы, плагины, `mu-plugins`, drop-ins, конфигурацию `wp-config.php`, маршрутизацию, конфиги служб и необходимые приватные файлы загрузок. Для внешней медиатеки предусмотреть отдельный согласованный снимок. В манифесте указать версии ядра/PHP/БД/плагинов, UTC, site ID и environment, состав, размеры и SHA-256 файлов. Ядро и системные зависимости восстанавливаются из закреплённых пакетов. Зависимости на внешний менеджер секретов описываются ссылками на версии, с отдельной процедурой восстановления доступа. [WooCommerce HPOS](https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/)
3. **Шифрование и передача.** Архив со SQL, конфигами и манифестом шифруется `age` на источнике публичными ключами восстановления для этой пары сайт/окружение. Закрытые ключи для проверочного восстановления доступны только выделенной службе восстановления и в отдельном хранилище для владельца. Ключи сохраняются для старых архивов до истечения retention. Передача по HTTPS в приватный Backblaze B2 через S3 API. Уникальные имена объектов, минимальные права записи без чтения и удаления, отдельный read-only доступ для проверки. Объект отмечается готовым после подтверждения размера и независимого чтения с проверкой SHA-256 шифротекста. Признак готовности привязан к конкретной версии объекта. Сырые данные обрабатываются в закрытом временном рабочем каталоге и удаляются по завершении. В логи и GitHub идут только статусы и безопасные идентификаторы. [age](https://github.com/FiloSottile/age) · [Backblaze B2](https://www.backblaze.com/docs/cloud-storage-about-backblaze-b2-cloud-storage)
4. **Хранение.** Полные независимые архивы в пилоте. Staging — все снимки за последние сутки, по одному дневному до 7 дней и по одному недельному до 28 дней. Production — все плановые снимки за последние 7 дней, по одному ежедневному до 30 дней, по одному еженедельному до 90 дней. Полные предрелизные копии — 30 дней. Retention применяется по классам копий и UTC. Object Lock на версию минимум 7 дней, для длительных классов — до конца их срока. Снимки младше 7 дней учитываются в объёме даже после выхода из короткого класса хранения. Отдельная роль удаляет истёкшие версии после проверки наличия достаточных валидных копий. Ротация прекращается при провале проверок. Перед применением к данным покупателей владелец утверждает сроки, регион, доступ и порядок обработки запросов на удаление. [Backblaze Object Lock](https://help.backblaze.com/hc/en-us/articles/360052973274-Object-Lock-FAQs)
5. **Контроль.** Внешний монитор с доступом только к сводке сигналов проверяет свежесть, готовность и просрочку restore drill. При первой ошибке — уведомление и один повтор с задержкой, при пропущенном сроке — аварийный статус и блокировка следующего релиза. Последняя валидная копия остаётся доступной, неудачная выгрузка не заменяет её.

**Критерии приёмки.** До первого релиза, после смены инструмента, версий платформы или ключей и далее по расписанию восстанавливать копию в чистую среду. Еженедельно проверять staging, ежемесячно — production после отдельного допуска к обработке данных. Для production использовать выделенную закрытую среду восстановления с запретом внешнего трафика по умолчанию. Перед запуском WordPress заменить runtime-конфигурацию, исключить реальные платежи, очереди, вебхуки, почту и фоновые интеграции. Рутинный staging использует синтетические данные.

| Проверка | Условие PASS |
| --- | --- |
| Доставка и целостность | Независимый проверяющий скачал ожидаемую версию из внешнего bucket, сверил SHA-256, расшифровал архив нужным ключом и сверил каждый файл с манифестом. Пара сайт/окружение совпала, повреждённая или неполная копия отклонена. |
| БД и файлы | Импорт без ошибок в пустую БД. Сверены перечень таблиц, ожидаемые контрольные значения из того же среза, активная тема/плагины, права, выбранные вложения и чтение заказов через WooCommerce API для текущего режима HPOS. Отчёт содержит только агрегаты и результат без персональных данных. |
| Приложение и восстановление | Базовые страницы и WooCommerce smoke проходят. Контрольный тест подтверждает блокировку внешних отправок. Измеренные RPO и RTO в пределах цели. Зафиксированы backup ID, версии, время, результат и причина отказа, если есть. Временные данные и ключевой доступ сеанса удалены. |
| Отказоустойчивость | Тест повреждённой копии, неверного ключа и недоступного хоста подтвердил отказ с уведомлением. В отдельной репетиции выполнено восстановление из B2 без исходного сервера с запасным доступом к ключу. |

## 4. Staging deployment и откат

**Основной транспорт — SSH в выделенный Linux VPS.** Ключ ограничен фиксированной серверной командой без shell-доступа, forwarding и произвольных путей. GitHub Actions проверяет pinned host key, передаёт манифест и ZIP. Серверный обработчик валидирует профиль, SHA-256 и пакет, затем вызывает WP-CLI от staging UID. Отдельный SFTP допустим для приёмки файлов во входящем каталоге с серверным обработчиком. Для управляемого хостинга допустим документированный API с поддержкой scoped credentials, статуса операций, проверки артефакта и отката. Доказательства доступности каждого варианта собираются при подключении стенда.

1. **Триггер и preflight.** После отдельного разрешения на подключение staging брать кандидата из защищённого `main` с зелёным CI. Для пакетов с миграцией — отдельный режим. Проверить домен, environment, `home`/`siteurl`, версии, свободное место, базовый health, доступность проверенной резервной копии, сохранённый предыдущий релиз и выключенные боевые интеграции. Проверки с несовпадением прекращают операцию до записи. Хост сериализует релизы и бэкапы блокировкой пары сайт/окружение. Новый релиз устаревшего SHA пропускается после проверки актуального кандидата. GitHub concurrency дополняет серверную блокировку.
2. **Подготовка и переключение.** Для пилота ограничиться темой с заранее выбранным активным slug и без миграций или настройки витрины. Распаковать ZIP в отдельный каталог релиза, сверить манифест, права и регулярные файлы. На одной файловой системе переключить ссылку стабильного пути темы атомарным переименованием ссылки. Конфиг, media и БД остаются отдельными постоянными ресурсами. Первый стенд заранее проверяет поддержку такой схемы ядром, PHP и cache/OPcache. Работоспособность сохраняется при недоступности веб-админки. Выполнить перезагрузку нужного кэша и подтвердить активный slug и release ID. Установка и обновления плагинов/ядра подключаются отдельным этапом с тестом совместимости и планом миграции.
3. **Health и smoke.** Установить лимит 5 минут и не более трёх попыток для временных сетевых ошибок. Проверить TLS, точный хост и ожидаемый release ID с обходом кэша стенда, вход в админку тестовой учёткой, отсутствие PHP fatal, наличие активных WooCommerce и темы, опубликованные назначенные страницы. Браузер проверяет главную, мобильное меню, каталог, карточку товара, количество и итог корзины, checkout с непустой корзиной и тестовый аккаунт. Полный заказ с офлайн-оплатой проходит в одноразовом изолированном окружении. На постоянном стенде отправка checkout допускается только для синтетических заказов в отдельно включённом тестовом режиме.
4. **Автоматический откат темы.** Записать журнал перехода с предыдущим release ID и крайним временем проверки до переключения. Если обязательный health не проходит, под блокировкой вернуть предыдущую ссылку и активную тему при необходимости, сбросить кэш и повторить health. Таймер на хосте обнаруживает незавершённое переключение даже после обрыва SSH или завершения runner. БД не перезаписывается автоматически. Для изменений схемы нужна предварительная репетиция совместимого отката или план исправления вперёд. Если откат не прошёл, заморозить очередь релизов и отправить владельцу инструкцию по восстановлению с backup ID.
5. **Уведомления.** Job публикует итог в GitHub Actions и отправляет владельцу оповещение по выбранному приватному каналу при сбое, откате, пропуске RPO или запросе approval. В сообщении — сайт, окружение, commit SHA, release/backup ID, время, статус и ссылка на запуск. Успешные события остаются в журнале. Аварийный сигнал о пропавшем runner или таймере приходит от внешнего монитора.

**Критерий перехода уже выполнен.** Для автоматизации требуются сохраняемые релизы, поддерживаемый удалённый исполнитель и проверяемый внешний бэкап. Legacy-стенд Free оставить для отдельно одобренных ручных операций. Пока новый хост не принят, Compose CI остаётся каналом проверки кандидатов.

Перед покупкой подтвердить поддержку неперсональных SSH-ключей с ограничениями или эквивалентного API, WP-CLI, доступа к MariaDB на хосте, таймеров, исходящего HTTPS до bucket, доступа smoke runner к стенду по TLS, изоляции БД и пользователей, независимой консоли и аварийного восстановления. При двух релизах, одном бэкапе и тестовом восстановлении запас места должен оставаться ≥25%. Проверочная репетиция на новом одноразовом стенде должна показать сохранность после переподключения, чтение полного ZIP и архива по хешу, отсутствие доступа ключа к другому сайту, фактическую блокировку unapproved production job в тестовой модели, восстановление и автоматический откат при искусственном сбое. Зафиксировать выводы в PR внедрения. STAGE-011 подтверждает документированные примитивы, а приёмка доступов и работы на купленном тарифе остаётся будущей проверкой.
