# STAGE-015 · WordPress Factory AI Control Center

Мобильная панель управляет той же очередью SQLite, что и CLI STAGE-014. Веб-процесс проверяет доступ и ставит задачи, диспетчер исполняет их независимо от браузера. Два проекта могут использовать разные Git-репозитории, профили WordPress, бюджеты и права пользователей. [Оркестратор](STAGE-014.md) · [Сервер Factory](STAGE-013.md)

## Демонстрация

Из checkout на Linux с Python 3.11+, Git и Node.js выполните:

```bash
umask 077
demo="$(mktemp -d)"
python3 -B -m factory.control.demo "$demo"
python3 -B -m factory.orchestrator --config "$demo/projects.json" --state "$demo/state" run &
dispatcher=$!
trap 'kill "$dispatcher" 2>/dev/null || true' EXIT
python3 -B -m factory.control --config "$demo/projects.json" --accounts "$demo/accounts.json" \
  --state "$demo/state" --origin http://127.0.0.1:8787
```

Откройте `http://127.0.0.1:8787`, войдите как `owner` с выведенным паролем и подключите оба профиля. В каждом проекте поставьте бизнес-задачу. Оркестратор создаст цепочку планирования, архитектуры и разработки. Mock выдаёт синтетические предложения и ревью. Git-коммиты, проверки, зависимости и статусы выполняются и сохраняются в отдельных локальных репозиториях. Компактная демонстрация не требует Docker. Полный сценарий ниже добавляет два временных Docker-сайта и копирование с восстановлением.

## Подключение к выделенному тестовому контуру

1. Создайте защищённый реестр по примеру STAGE-014. Для каждого проекта укажите отдельный тестовый репозиторий и, если нужен WordPress, профиль с уникальными ID и loopback-портом. Используйте только предназначенные для этого контура синтетические данные. Идентификатор проекта сохраняется за одним проектом на протяжении жизни каталога состояния. [Пример реестра](../factory/orchestrator/projects.example.json)
2. Сгенерируйте хеш для каждой учётной записи через `python3 -B -m factory.control --hash-password`. Создайте принадлежащий оператору файл JSON с правами `0600`. К возвращаемым полям `salt` и `hash` добавьте права пользователя. Верхний уровень файла сопоставляет логины объектам учётных записей. У владельца `"owner": true`. У делегированного пользователя `"projects": {"example-store": "operator"}` или право `viewer`. Для изменения прав перезапустите панель. Регистрация профиля в панели доступна владельцу.
3. Запустите один диспетчер и один веб-процесс с одинаковыми `--config` и `--state` во внешнем каталоге с правами `0700`. Используйте отдельную системную учётную запись Factory. Параметр `--port` по умолчанию равен 8787. Веб-процесс слушает loopback. Для iPhone поставьте перед ним TLS reverse proxy на отдельном тестовом домене и задайте точный публичный URL через `--origin`. Прокси должен сохранять исходный `Host` и передавать `Origin`. Например, в отдельном блоке Caddy используйте `reverse_proxy 127.0.0.1:8787`. Ограничьте доступ к домену через приватную сеть или существующий VPN.
4. Откройте HTTPS-адрес в Safari. В меню «Поделиться» выберите «На экран „Домой“». Service worker сохраняет общедоступную оболочку. Авторизованные данные, операции и уведомления требуют сети. Уведомления отображаются в панели при опросе очереди.

Стенд панели использует команды локального тестового профиля STAGE-014, включая `start`, `health`, `backup` и `restore`. В списке снимков доступны только ID и время. Factory повторно проверяет профиль и целостность снимка перед восстановлением. Поле здоровья показывает последнюю проверку, а открытый журнал указывает на необходимость восстановления через штатный CLI. Выделенные SSH-окружения и off-site restic STAGE-013 обслуживаются прежними командами. [Восстановление локального Factory](STAGE-012.md) · [Операции выделенного сервера](STAGE-013.md)

## REST API

Базовый путь `/api/v1`. Изменения принимают JSON и требуют совпадающий `Origin`. Вход принимает `username` и `password`, сессия передаётся через HttpOnly cookie с `SameSite=Strict`. На HTTPS также используются `Secure` и префикс `__Host-`. Срок сессии — восемь часов, перезапуск веб-процесса сбрасывает сессии. Лимит неверных входов действует на экземпляр панели. Аудит хранит успешные изменения, решения владельца и входы с отметками времени в приватной SQLite.

| Метод и путь | Действие |
| --- | --- |
| `POST /session`, `POST /logout` | Вход и завершение сессии |
| `GET /projects`, `POST /projects/:p/register` | Видимые проекты и подключение доверенного профиля владельцем |
| `GET /projects/:p`, `GET /projects/:p/tasks/before/:id` | Состояние проекта и страницы очереди |
| `POST /projects/:p/business` | `objective`, разрешённая `role`, опционально `priority` и массив `after` |
| `POST /projects/:p/operations` | `operation`, `objective`, при необходимости полный Git `ref` или ID `backup` |
| `POST /projects/:p/pause`, `POST /projects/:p/resume` | Управление выдачей задач одного проекта |
| `GET /projects/:p/tasks/:id` | Результат, этап, попытка, зависимости, события и версия разрешения |
| `POST /projects/:p/tasks/:id/{hold,release,cancel,retry}` | Остановка на границе этапов, возобновление, отмена и новая попытка |
| `POST /projects/:p/tasks/:id/approve` | Владелец передаёт точные `operation` и `version` из задачи |
| `POST /projects/:p/budget` | Владелец задаёт `limit_microdollars` в пределах бюджета реестра |
| `GET /projects/:p/audit` | Последние события аудита проекта для владельца |

Оператор может ставить задачи и управлять их ходом в своём проекте. Читатель видит только очередь и результаты назначенных ему проектов. Клиент получает сведённые поля задачи, PR и проверок. Пути к рабочим каталогам, привилегированные настройки, сериализованные снимки и ключи остаются на сервере. Доступ к API проверяется отдельно для каждого проекта, задачи и зависимости.

Остановка действует на следующий этап. Запущенный внешний шаг может закончиться, поэтому панель сохраняет фактический результат и отдельно показывает запрошенную отмену. Повтор создаёт новый ID и сохраняет исходную задачу. При ошибке критического шага сначала проверьте журнал Factory, выполните необходимое восстановление через CLI и снимите общую аварийную паузу операторской командой. Версия разрешения включает ID задачи и проекта, отпечаток регистрации, параметры операции и попытку. Сборка и публикация используют конкретный доверенный SHA. Восстановление использует конкретный снимок. Повторное подтверждение того же поручения отклоняется.

## Реальный исполнитель и расходы

Панель использует адаптер OpenAI Responses из STAGE-014. Сверены официальные контракты `POST /v1/responses/input_tokens`, `POST /v1/responses`, строгий `text.format`, `max_output_tokens` и `usage`. Оплачиваемый вызов требует `executor: "responses"`, проектного ключа в окружении диспетчера и отдельного `FACTORY_AUTHORIZE_PAID_AI=1`. Веб-процесс этих переменных не требует. Указывайте актуальные верхние цены в бюджете проекта. Модель формирует предложения и отчёты без вызова инструментов. Оркестратор проверяет изменяемые файлы и ведёт PR до ручного решения. Панель требует профили с выключенным автослиянием. [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) · [Подсчёт входных токенов](https://developers.openai.com/api/reference/resources/responses/subresources/input_tokens/methods/count) · [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

Резерв начисляется до запроса, учитывает худший случай и сохраняется после неоднозначного ответа. Статистика токенов и оценки в USD появляется по подтверждённому `usage` и настроенным ставкам. Лимит 0 запрещает новые резервы. Изменение лимита не прерывает уже начатый вызов. Для независимых ключей запускайте диспетчеры разных контуров с отдельными каталогами состояния и реестрами.

## Проверки и откат

```bash
python3 -B -m unittest discover -s tests -v
python3 -B -m unittest discover -s factory/tests -v
npm install --no-save --package-lock=false playwright-core@1.56.1
npx playwright-core install --with-deps chromium webkit
python3 -B factory/tests/control_lifecycle.py --wordpress --browser
```

До изменения управление STAGE-014 выполнялось через CLI. Новый job Factory CI сохраняет снимки панели на широком экране и мобильных viewport. Chromium проверяет ширины 375, 390, 768, 1024 и 1440 px, WebKit использует профиль iPhone 13 и ширины 375 и 390 px. Это автоматическая эмуляция, физический iPhone требуется для проверки установки на устройство. HTTP-сценарий использует два реальных изолированных Git-проекта. При `--wordpress` поднимаются временные WordPress и WooCommerce и проверяется восстановление состояния из снимка через API. Провайдер AI в этих сценариях — mock. Реальные Responses и удалённая публикация агента не тестируются этими сценариями. [Workflow Factory](../.github/workflows/factory.yml)

Для отключения панели остановите веб-процесс и снимите его маршрут с TLS-прокси. Чтобы остановить работу очереди, приостановите диспетчер, дождитесь завершения внешних шагов и сохраните приватный каталог состояния. Для диагностики используйте штатный CLI той же версии. Перед возвратом к STAGE-014 разберите оставшиеся задачи и удержания. Старый диспетчер не учитывает управление паузами, удержаниями и лимитами, введённое в STAGE-015.
