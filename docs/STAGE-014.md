# STAGE-014 · Автономный оркестратор WordPress Factory

Оркестратор выбирает доступные задачи из SQLite, выполняет их в независимых Git-клонах и сохраняет этапы, результаты и события между перезапусками. Зависимости разблокируются после успешного завершения. Из доступных задач первой запускается задача с большим приоритетом, затем более ранняя. Независимые репозитории и сайты могут работать параллельно. Задачи одного Git-репозитория сериализуются, включая ожидание CI и ревью. Операции над сайтом дополнительно используют штатную блокировку Factory. [Очередь этапов](../factory/queue.json) · [STAGE-012](STAGE-012.md) · [STAGE-013](STAGE-013.md)

## Регистрация и управление

Нужны Linux, Python 3.11+, Git и GNU coreutils. Для локальных сайтов нужны Docker, Compose v2 и curl. Реестр JSON принадлежит пользователю запуска. У проекта есть ID, адрес репозитория, базовая ветка, тип сайта, тестовый домен, окружение, разрешённые операции и роли, пути исходников и контекста, профиль WordPress, бюджет и начальная очередь. Для локального репозитория путь считается относительно реестра. Профили используют разные ID и порты loopback. Реестр принимает окружение `test` и домены `.test` или `localhost`. [Пример конфигурации](../factory/orchestrator/projects.example.json)

Подставьте существующую локальную ветку проекта в поле `base`. Из доверенного checkout выполните:

```bash
state="$(mktemp -d)"
orchestrator() {
  python3 -B -m factory.orchestrator \
    --config factory/orchestrator/projects.example.json --state "$state" "$@"
}
orchestrator business example-store 'Обновить описание тестовой темы' --role wordpress
orchestrator run --workers 2
```

В другом терминале используйте тот же каталог состояния. `run` обслуживает очередь постоянно, `run --once` завершает процесс, когда нет готовых задач. Для отложенных повторов и опроса GitHub оставляйте `run` запущенным под менеджером процессов. Каталог состояния должен находиться вне Git, принадлежать пользователю запуска и иметь права `0700`. Храните его на локальной файловой системе. Один диспетчер владеет состоянием, остальные CLI-клиенты могут читать очередь и записывать команды управления.

| Команда | Действие |
| --- | --- |
| `business PROJECT OBJECTIVE --role ROLE` | Создаёт задачи планирования и архитектуры при наличии ролей, затем разработку. Готовые отчёты передаются зависимым задачам. |
| `submit PROJECT OPERATION OBJECTIVE` | Добавляет одну задачу. Для AI укажите `--role`, для сборки или публикации `--ref SHA`, для восстановления `--backup ID`. |
| `seed PROJECT` | Ставит записанную в реестре последовательность. Каждый вызов создаёт новый набор задач. |
| `list`, `get ID`, `events ID`, `status` | Возвращают JSON со статусами, результатом, событиями задачи и состоянием диспетчера. |
| `pause`, `resume`, `cancel ID` | Управляют следующими этапами. Уже начатая внешняя операция может завершиться. |
| `approve ID OPERATION` | Одобряет конкретную неизменяемую операцию Factory и её параметры. |
| `approve ID SHA` | Подтверждает слияние указанной ревизии в разрешённом GitHub-проекте. |

`--priority` принимает значения от −100 до 100. Повторяйте `--after ID` для зависимостей внутри проекта. Задачи с неуспешной зависимостью переходят в `blocked`. Код и отчёты повторяются в пределах `max_attempts` и `retry_seconds`. Для операций Factory, меняющих сайт, действует одна попытка. Критическая ошибка приостанавливает диспетчер. После прерывания такого шага изучите журнал Factory и выполните согласованное восстановление перед новой попыткой. После обычного прерывания диспетчер возвращает задачу в очередь, сохраняя счётчик попыток и контрольную точку публикации.

CLI требует доступа к выделенной учётной записи Linux и приватному каталогу состояния. JSON-ответы и коды завершения дают интерфейс для будущего Telegram-бота или мобильной панели. Публичный сервер отсутствует. При подключении клиента его доверенный посредник должен проверять пользователя, а подтверждения выполнять через отдельную привилегированную команду.

## Исполнители и бюджеты

Десять конфигураций описывают роли, разрешения, инструменты, вход, выход и критерии готовности. Исполнитель запускается по требованию для выбранной роли. В локальной демонстрации `mock` даёт детерминированное предложение и синтетическое ревью. Вариант `responses` отправляет отдельные запросы для работы и независимого QA или Security Review. Роль ревью получает diff и результаты проверок. [Конфигурация ролей](../factory/orchestrator/roles.json)

Responses API использует строгое JSON-описание отчёта, ревью или списка замен файлов. У модели отсутствуют инструменты, shell, доступ к рабочей директории и учётным данным GitHub. Выбранные файлы, задача и обратная связь передаются как недоверенные данные. Оркестратор принимает изменения только существующих обычных UTF-8 файлов из allowlist, ограничивает размер, проверяет diff и создаёт коммит на ветке задачи. Выбирайте контекст без секретов и клиентских данных. Тестовый CI должен запускаться на одноразовых runner без секретов, с ограниченными правами и без доступных публикаций. Для локального режима обязательны проверка diff и отдельный вызов review; прикладные проверки добавляются в CI тестового проекта. [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) · [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

Для `responses` задайте в `budget` имя модели, `max_input_tokens`, `max_output_tokens`, актуальные верхние цены в микродолларах за миллион входных и выходных токенов (`input_microdollars_per_million`, `output_microdollars_per_million`) и `total_microdollars`. Для запуска отдельно требуется `FACTORY_AUTHORIZE_PAID_AI=1` и проектный `OPENAI_API_KEY`. Бюджет проверяется транзакционно до сетевого запроса, резерв рассчитывается по верхнему пределу и сохраняется в SQLite. Резерв не возвращается после отказа или неоднозначного результата, поэтому очередь может остановиться раньше достижения фактического расхода. API считает входные токены перед генерацией и ограничивает выход в запросе. Денежная оценка зависит от актуальности цен и охватывает обращения этого диспетчера. [Подсчёт входных токенов](https://developers.openai.com/api/reference/resources/responses/subresources/input_tokens/methods/count)

## GitHub и Factory

Чтобы подключить GitHub, используйте отдельный тестовый репозиторий, `repository: "owner/repo"`, `executor: "responses"` и объект `github` с `trusted_test_ci: true`, именами `required_checks` и `timeout_seconds`. Нужны GitHub CLI и `FACTORY_GITHUB_TOKEN`, ограниченный этим репозиторием. Код публикуется на ветке задачи без force push. При повторном запуске диспетчер использует существующий PR для этой ветки. Проверки опрашиваются по SHA, а сбои передаются на следующую попытку с именем проверки, результатом и предыдущим diff. При внешней смене SHA оркестратор останавливается. Зависимые задачи ждут подтверждённого GitHub слияния. Проверьте, что выбранная учётная запись запускает workflows по push или PR. [GitHub Check Runs](https://docs.github.com/en/rest/checks/runs)

Параметр `github.auto_merge` по умолчанию выключен. Для разрешённого тестового репозитория нужны явное включение, заданный независимый `github.reviewer`, одобрение той же ревизии владельцем через CLI, успешный AI review и обязательные проверки. Оркестратор проверяет непротиворечивость PR и настройки защиты ветки, включая запрет обхода администраторами, актуальность тестов и сброс устаревших ревью. GitHub получает запрос с ожидаемым SHA и применяет branch protection. Используйте выделенную учётную запись без прав обхода защиты. При конфликте состояние PR остаётся доступным для диагностики, слияние ждёт исправления в пределах заданного срока. [Слияние с проверкой SHA](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

Операции `build`, `start`, `deploy`, `health`, `backup`, `rollback` и `restore` используют проверенные команды Factory. Профиль и `factory_source` задаёт оператор. Сборка берёт только точный SHA из истории доверенной локальной базовой ветки. `health` проверяет WordPress, тему, главную, каталог, карточку товара и добавление в корзину WooCommerce. `deploy` использует журнал и автоматический откат Factory при падении smoke. `restore` проверяет ID, профиль и целостность снимка. Сайты работают на loopback, запасные копии локального контура лежат в приватном состоянии. Для остановки оркестратора при откате STAGE-014 приостановите очередь и завершите процесс после текущих операций. Сохраните его состояние и используйте штатный CLI Factory для журнала и восстановления. [Команды и восстановление Factory](STAGE-012.md)

## Воспроизводимые проверки

```bash
python3 -B -m unittest discover -s tests -v
python3 -B -m unittest discover -s factory/tests -v
python3 -B factory/tests/orchestrator_lifecycle.py
python3 -B factory/tests/orchestrator_lifecycle.py --wordpress
```

В сценарии используются два реальных независимых локальных Git-репозитория. Mock ограничен выдачей предложений и ревью. Проверка фиксирует приоритет, зависимые шаги, изолированные ветки и коммиты, ошибку `git diff --check`, автоматический повтор, запрещённую роль и операцию, фактическое завершение диспетчера через SIGKILL и восстановление очереди. В режиме `--wordpress` поднимаются два реальных Docker-экземпляра с синтетическими данными. Сценарий проверяет сборку, одобрение, старт, WooCommerce smoke, копирование, восстановление, публикацию и откат после намеренной ошибки. Модульные тесты удалённых адаптеров проверяют ответы-заглушки. Платные Responses и удалённый автономный цикл GitHub в рамках этого этапа не запускались. CI запускает новый сценарий вместе с существующими проверками. [Workflow Factory](../.github/workflows/factory.yml)
