# STAGE-002 · Публикация темы на тестовый WordPress

Целевой сайт — https://top-pariks-test.freehosting.dev. Workflow **TOP-PARIKS staging** запускается вручную из `main`. Операция `deploy` запускает **TOP-PARIKS CI** для выбранного коммита `main` и использует артефакт этого же запуска после успешных проверок. При изменении `main` после запуска версия кандидата остаётся привязанной к SHA в Actions.

## Архив темы

CI собирает `theme/top-pariks/` командой `git archive` и сравнивает файловое содержимое с корневым `top-pariks.zip`. Из артефакта **top-pariks-theme** Actions извлекает внутренний `top-pariks.zip`. В нём один каталог `top-pariks/` с `style.css` (заголовок и версия темы), `index.php`, шаблонами PHP и `assets/`. Перед SSH workflow проверяет имена, типы и содержимое записей ZIP по исходникам выбранного коммита. Сервер проверяет SHA-256 и целостность ZIP перед извлечением.

## Доступные способы публикации

| Способ | Что нужно подтвердить |
| --- | --- |
| **SSH + WP-CLI** (реализовано) | Доступ по ключу со стороны runner, команды оболочки, WP-CLI и права SSH-пользователя на запись в один каталог темы. WP-CLI проверяет идентичность сайта и активную тему. SSH передаёт ZIP и даёт серверу выполнить замену и восстановление. [WP-CLI](https://developer.wordpress.org/cli/commands/theme/) |
| **SFTP** | Подтвердить доступ по SFTP, проверку ключа сервера и права на чтение, загрузку и переименование каталогов. SFTP передаёт файлы. Для проверки WordPress и активации нужен отдельный канал, например WP-CLI или админка. |
| **WordPress REST API** | Штатный endpoint тем поддерживает чтение. Для установки ZIP и активации потребовался бы отдельный поддерживаемый интерфейс с соответствующими правами. [WordPress REST API](https://developer.wordpress.org/rest-api/reference/themes/) |
| **Панель или API хостинга** | В панели аккаунта или у поддержки подтвердить провайдера, тариф, доступные протоколы и операции резервного копирования. При наличии только админки или файлового менеджера оператор может установить ZIP вручную. Для автоматизации на тарифе без SSH понадобится поддерживаемый API с операциями замены и восстановления или отдельный стенд с SSH. |

InfinityFree предлагает `freehosting.dev` как бесплатный поддомен. Для бесплатного тарифа провайдер указывает FTPS, а поддержка SSH и SFTP отсутствует. Защита бесплатных сайтов также ограничивает автоматические HTTP-запросы. Проверьте тариф именно этого аккаунта в панели. Если это бесплатный тариф InfinityFree, для данного workflow понадобится стенд с SSH и WP-CLI. [Поддомены InfinityFree](https://forum.infinityfree.com/t/11-new-free-subdomain-options-now-available/118868), [SSH и FTPS](https://forum.infinityfree.com/t/how-can-we-use-ssh/79234), [Ограничения доступа по HTTP](https://forum.infinityfree.com/t/why-isnt-api-access-working-on-my-website/115198/1)

Доступ к shell, SFTP и WP-CLI для этого аккаунта пока не подтверждён. У владельца также была зафиксирована заглушка Coming Soon. Перед первым запуском проверьте её текущий статус и возможность получить страницы тестового сайта с сервера по HTTPS. [STAGE-001 #13](https://github.com/TonyGoalsMan1/top-pariks/issues/13)

## Настройка перед первым запуском

1. Подтвердите отдельные файлы и базу данных стенда, доступ к панели для аварийного восстановления и корректные значения `home` и `siteurl` для целевого домена. Workflow рассчитан на отдельную установку с каталогом `wp-content/themes`. Мультисайт блокируется. Проверьте, что у стенда отключены реальные оплаты, исходящая почта и рабочие интеграции.
2. Выделите отдельного непривилегированного SSH-пользователя и ключ для staging. На сервере нужны Bash, WP-CLI в `PATH`, GNU coreutils, `find`, `flock`, `unzip` и `curl`. Пользователь должен иметь доступ к конфигурации тестового WordPress и право заменить каталог темы. Создайте закрытый каталог резервных копий вне всех веб-корней на том же файловом разделе, что и `wp-content/themes`. Владелец — SSH-пользователь, права — `0700`. Сверьте SSH host key по панели или с поддержкой через доверенный канал. Для нестандартного порта запись в `known_hosts` начинается с `[host]:port`.
3. В GitHub откройте **Settings → Environments → staging**. Ограничьте развёртывание веткой `main`, назначьте обязательного ревьюера и отключите обход правил администратора, если доступно. Заполните **Environment secrets**. [GitHub Environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

| Secret | Значение |
| --- | --- |
| `STAGING_SSH_HOST` | SSH-имя сервера или IPv4 из панели хостинга |
| `STAGING_SSH_PORT` | Порт SSH |
| `STAGING_SSH_USER` | Отдельная учётная запись для стенда |
| `STAGING_SSH_KEY` | Приватный ключ для неинтерактивного входа |
| `STAGING_SSH_KNOWN_HOSTS` | Проверенная запись публичного ключа SSH-сервера |
| `STAGING_WP_PATH` | Абсолютный путь к тестовому WordPress |
| `STAGING_BACKUP_PATH` | Абсолютный путь к закрытому каталогу резервных копий |

Добавляйте значения непосредственно в GitHub Environment. Для проверки подключения используйте команды чтения на хостинге, например `wp --path=<путь> option get home`, `option get siteurl`, `theme list` и `plugin is-active woocommerce`. Для установки нужны активный WooCommerce, опубликованные страницы магазина, корзины и оформления, а также доступный серверу HTTPS-ответ без перенаправления для главной, магазина и корзины. Если защита выдаёт заглушку или challenge, согласуйте с владельцем способ проверять страницы через разрешённый доступ. Workflow не меняет видимость сайта.

## Развёртывание и приёмка

1. После разрешения владельца выберите **Actions → TOP-PARIKS staging → Run workflow → main → deploy** и оставьте `backup_id` пустым. Ревьюер сверяет SHA и окружение перед одобрением.
2. Сервер сохраняет под идентификатором запуска прежний каталог `top-pariks` либо признак его отсутствия, а также slug активной темы. Затем устанавливает файлы и при необходимости активирует `top-pariks`. Действие ограничено каталогом этой темы и штатной сменой активной темы через WP-CLI. Товары, настройки WooCommerce и остальные темы не затрагиваются.
3. Workflow проверяет активную тему и WooCommerce через WP-CLI, опубликованные страницы магазина, корзины и оформления, HTTP 200 на главной, в магазине и корзине и наличие шапки TOP-PARIKS после установки. Проверки запускаются без заказа. CI отдельно проверяет оформление в изолированной базе с тестовой оплатой.
4. Запишите SHA и **Staging backup ID** из журнала. В браузере проверьте главную, версию активной темы в админке, каталог, тестовый товар, корзину и оформление до отправки заказа. Сверьте отсутствие критических ошибок в журнале WordPress и PHP. Проверка живого сайта выполняется после согласованной публикации.

## Откат

При ошибке замены, активации или проверки скрипт восстанавливает прежний каталог и активную тему. Запуск при этом завершается ошибкой. Чтобы вернуться к состоянию до успешной публикации, запустите тот же workflow из `main` с операцией `rollback` и её **Staging backup ID**. Откат тоже сохраняет состояние перед изменением, поэтому его можно отменить с помощью нового идентификатора.

Копии лежат на сервере в `STAGING_BACKUP_PATH/<backup_id>`. Храните их приватно и следите за свободным местом. При аварийном завершении процесса или отключении файловой системы оператор восстанавливает из каталога запуска сохранённый `top-pariks` (файл `absent` означает, что каталог изначально отсутствовал), затем сверяет и при необходимости активирует тему из файла `active-theme` через WP-CLI. Перед ручным восстановлением убедитесь, что скрипт больше не работает. Переместите текущий `top-pariks` в закрытый каталог для диагностики. Остальные темы и БД для такого восстановления оставьте на месте.
