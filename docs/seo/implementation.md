# SEO-001 · Технические правила и план внедрения

## Индексация и canonical

| Ответ | Индексация | Canonical и обход | Sitemap |
| --- | --- | --- | --- |
| Главная, каталог, категория, карточка, опубликованная статья | Разрешить для качественных страниц с 200 | Один абсолютный HTTPS self-canonical на выбранном хосте | Да |
| Страница 2+ каталога или категории | Разрешить при наличии товаров | Self-canonical на каждую страницу. Последовательные HTML-ссылки, URL за пределом пагинации возвращает 404 | Нет |
| Сортировка и tracking | Сортировку исключить при помощи noindex. Tracking оставить доступным с canonical | Сортировка с изменившимся набором на странице получает self-canonical. При доказанной эквивалентности сортировки или tracking использовать чистый эквивалент, сохраняя страницу пагинации. Для tracking сохранять атрибуцию | Нет |
| Рабочий фильтр с изменившейся выборкой | noindex, follow | Self-canonical на нормализованный URL. Параметры оставить доступными для считывания noindex. Не создавать сквозные ссылки на комбинации | Нет |
| Согласованная SEO-посадочная | Разрешить | Чистый URL с self-canonical, уникальный текст, ассортимент, ссылки из каталога. Эквивалентный фильтр можно канонизировать на посадочную после проверки полного совпадения, включая пагинацию. Для такого дубля использовать canonical без noindex | Да |
| Несуществующее значение или комбинация фасетов без результатов | Не индексировать | Для запрашиваемых URL вернуть 404 с восстановлением навигации. Проверить UX пустой выборки и сохранение состояния интерфейса | Нет |
| Поиск, корзина, checkout, аккаунт, избранное | noindex для доступных ответов с 200 | Оставить доступ к noindex. Защита приватных ответов обеспечивается авторизацией и правилами кеширования | Нет |
| Staging | Закрыть доступ извне | Авторизация или ограничение сети с noindex как дополнительным контролем. Сохранить `blog_public=0` | Не отправлять |

Проверить реальные параметры активного фильтра и сортировки, включая порядок и повтор значений, комбинации, тип запроса, сброс страницы при смене фильтра и сохранение выбора после возврата. Ограничить генерацию ссылок на бесконечные комбинации. Если роботы уже посещают такие URL, сначала дать им считать noindex. Ограничения обхода через robots.txt рассматривать по журналам после исключения из индекса и при отсутствии необходимости считывать noindex. CSS, JS и изображения для рендеринга должны оставаться доступными.

Выбрать один источник canonical, robots meta и XML sitemap после просмотра хуков WordPress и установленных плагинов. Проверить фактический ответ `/robots.txt`, конфигурацию CDN и веб-сервера, `/wp-sitemap.xml` и `/sitemap.xml`. Последний путь может отсутствовать. В robots.txt указать действующий sitemap абсолютным URL. В sitemap оставить конечные канонические страницы с 200, исключить служебные страницы, фасеты, пустые архивы и редиректы. Проверить каждый тип URL также на `X-Robots-Tag`, включая ответы кеша. Перед публикацией сверить правила в Google Search Console и Яндекс Вебмастере. Плагин выбирать только при доказанном пробеле, с оценкой конфликтов и после согласования.

## Структурированные данные

| Тип | Источник | Проверка |
| --- | --- | --- |
| Product | WooCommerce, одиночная карточка | Название, изображения, SKU, описание и бренд при наличии подтверждённых данных. SKU, MPN и GTIN имеют разный смысл |
| Offer / AggregateOffer | Текущая цена, валюта, наличие и варианты из WooCommerce | Сверить с видимыми ценой и наличием. Проверить вариант со скидкой, распроданный товар и переменные товары. Разметку рейтинга брать только из опубликованных отзывов |
| BreadcrumbList | Фактическая иерархия ссылки на главную, каталог, выбранную категорию и карточку | Сверить позиции, канонические адреса и согласованный путь. Проверить, вызываются ли хуки крошек в обёртке `woocommerce_content()` |
| Organization | Подтверждённые название, URL и логотип на главной или странице о компании | Стабильный `@id` с привязкой к продавцу при необходимости. Контакты и sameAs только из подтверждённых источников |

Сначала снять текущий JSON-LD и проверить источники вывода. Сохранять WooCommerce владельцем Product и Offer, пока тесты не обоснуют замену. Проверить Google Rich Results Test для Product и BreadcrumbList, Schema Markup Validator для всего графа и видимый HTML. Согласовать представление переменных товаров, включая ProductGroup при необходимости.

## Скорость и изображения

Снять мобильные Lighthouse-прогоны на главной, архиве, фильтре и карточке с реальными фото. Сделать три холодных прогона одного профиля, записать медиану и LCP-элемент. Цели в полевых данных на 75-м перцентиле отдельно по устройствам: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Проверять CrUX и Search Console при достаточном трафике, иначе собирать RUM с разбивкой по шаблону. Lighthouse TBT использовать как лабораторный ориентир отзывчивости, полевой INP измерять отдельно.

Для LCP-изображения сохранить приоритет загрузки и исключить lazy loading. Для hero и изображений ниже первого экрана добавить размеры или фиксированное соотношение сторон. Использовать WooCommerce и WordPress для `srcset` и `sizes`, создавать WebP или AVIF по размерам карточек, сжимать исходники с визуальной проверкой. Загружать изображения ниже первого экрана лениво. Alt описывает изображение в контексте ссылки, декоративные изображения получают пустой alt. Использовать долгий кеш версионированных ассетов. Измерить TTFB и влияние скриптов, ограничить CSS/JS на страницах, где они нужны. Исключить из общего кеша персонализированные ответы, корзину, checkout, кабинет и запросы с WooCommerce-сессией. Проверять работоспособность мини-корзины и цену с учётом валюты и настроек.

## SEO-002 · Очерёдность внедрения

1. P0. Снять read-only инвентарь production и карту доступности. Утвердить правила индексации и хозяев метатегов. Проверить защиту staging и выключить показ демонстрационных цен на production до допуска к индексации.
2. P1. На изолированном стенде настроить шаблоны заголовков, метаданных и маршрутизацию фасетов в отдельной ветке. Согласовать изменения семантики и размещения текста с TOP Design.
3. P1. Проверить чистые и параметрические URL, sitemap, schema, 404, поиск и пагинацию по HTTP, отдельно прогнать гостевую покупку, вариации и кеш. Разделять проверку публичной конфигурации и staging с `blog_public=0`.
4. P2. После утверждения владельцем опубликовать утверждённую конфигурацию и контент. Сверить robots и sitemap сразу после релиза, далее отслеживать исключённые URL, ошибки 404, индексирование, клики и CWV. При регрессии откатить изменённую конфигурацию и отдельно перепроверить checkout.
