# STAGE-007 · Диагностика записи на staging FTPS

Ручной workflow **TOP-PARIKS staging FTPS write probe** проверяет, виден ли один диагностический файл в `MLSD` и доступен ли он через `RETR` после закрытия соединения и повторного входа. Результат относится к этому файлу и моменту проверки. История исчезновения маркера описана в [STAGE-005](STAGE-005.md) и [STAGE-006](STAGE-006.md).

## Запуск с iPhone

1. После появления workflow в `main` откройте репозиторий в Safari, затем **Actions → TOP-PARIKS staging FTPS write probe → Run workflow**. Если кнопка скрыта, в меню Safari выберите **Запросить настольный веб-сайт**.
2. Выберите `main`, введите `https://top-pariks-test.freehosting.dev` в поле **target**, оставьте **mode** в `dry-run`, а **confirmation** пустым. Откройте журнал job и проверьте `result=dry-run`. Этот режим проверяет ввод без секретов и сети.
3. Для пробы записи дождитесь отдельного разрешения. В **InfinityFree → Accounts → Manage → FTP Details** сверяйте домен, аккаунт и параметры окружения `staging-ftps`. Подтвердите, что `/top-pariks-backups` существует вне всех веб-корней, принадлежит только стенду и доступен для листинга, чтения и записи. Если права или изоляция неизвестны, запросите подтверждение у InfinityFree. На время пробы исключите изменения через файловый менеджер, другие FTPS-клиенты и внешнюю автоматизацию.
4. Откройте новую ручную отправку с тем же URL, выберите `probe` и введите `write one probe on top-pariks-test.freehosting.dev`. В журнале проверьте `write / STOR / accepted`, затем `after-write-list / MLSD / listed`, `after-write-read / RETR / read` и `verify / verified`. Сохраните время UTC и значение `test` из журнала. Повторная попытка того же запуска в GitHub не выполняет запись. Перед новой ручной отправкой разберите результат предыдущей.

Скрипт сверяет корень входа и ожидаемую структуру каталогов, генерирует случайный UUID и выполняет максимум один `STOR` по фиксированному абсолютному пути в закрытом каталоге. Перед записью он проверяет имя без учёта регистра в полном листинге и пробует прямое чтение. Найденное имя или доступный файл останавливают запись. `RETR 550` допускает как отсутствие, так и запрет чтения. У `STOR` нет атомарного режима «создать только при отсутствии». Случайное имя, проверки и выделенное окно без внешних записей снижают риск перезаписи. Общая группа GitHub Actions сериализует запись с публикацией темы и инициализацией маркера.

## Что проверить при сбое

| Результат | Ручная проверка |
| --- | --- |
| Отказ `MLSD` или неожиданная структура | Проверьте аккаунт и каталоги в закрытой панели. Уточните поддержку полного листинга и права в закрытом каталоге. |
| Отказ `STOR`, включая `550/552/553` | Проверьте права на запись вне веб-корня, квоты диска и inode, ограничения имён и типов файлов. При потере ответа проверьте, появился ли файл. |
| `STOR` принят, имя отсутствует в `MLSD`, `RETR 550` | Сверьте точный регистр, путь и аккаунт после нового входа. Попросите InfinityFree проверить фильтры, доступ и события хранения по времени UTC. |
| `MLSD` показывает файл, `RETR 550` | Проверьте права на чтение, блокировку файла и актуальность листинга. |
| `RETR` читает файл, листинг расходится | Проверьте фильтрацию `MLSD`, регистр и тип записи. |
| `sha256-mismatch` или `unexpected-size` | Проверьте точный файл в бинарном режиме и уточните, преобразует ли провайдер данные. |

При ошибке остановитесь и сохраните файл для расследования, если он появился. Передавайте провайдеру время UTC и безопасные поля `stage`, `command`, `reply`, `result`, `test`. Поле `reply=none` означает, что числовой ответ недоступен. [Диагностика FTPS](STAGE-004.md)

## Отдельная уборка после успешной пробы

После `result=verified` отдельно подтвердите удаление файла по идентификатору этого запуска. В доверенном explicit FTPS-клиенте с проверкой сертификата и защищённым каналом откройте тот же аккаунт стенда и `/top-pariks-backups`. Найдите точное имя `stage-007-probe-<test>.txt`. Скачайте файл в бинарном режиме и сверьте его со строкой `TOP-PARIKS STAGE-007 <test>`, за которой следует ровно один LF. При совпадении выберите только этот файл, проверьте имя в диалоге подтверждения удаления и обновите листинг после удаления. При любом расхождении остановитесь. Маркер и резервные копии не участвуют в уборке.

## Критерии готовности

PR открыт с выключенным автослиянием, CI проходит на локальных имитациях FTPS. Workflow записи доступен только через ручную отправку на `main` с точным подтверждением стенда. Живая проба требует отдельного разрешения. Для локальной проверки используйте `python3 -B -m unittest discover -s tests -v`.
