Все пять PR открыты на момент ревью. Доступные GitHub Actions на перечисленных HEAD завершились успешно. Проверено последовательное локальное объединение #31 → #32 → #33 → #34 → #35 от `main@0c91980`. Конфликтов нет. Интеграционная ветка сохраняет исходные коммиты и добавляет исправления пилота. Её можно принять одним merge commit после проверок, чтобы GitHub увидел исходные HEAD в истории `main`. При поэтапном слиянии сохраняйте коммиты, переводите базу следующего PR на актуальную `main`, заново проверяйте diff и дождитесь обязательных проверок. Затем примените исправления STAGE-016.

Перед любым слиянием, включающим #33, владелец проверяет в настройках GitHub, что `FACTORY_STAGING_ENABLED` отсутствует или имеет значение, отличное от `true`. Этот флаг разрешает workflow публикации при push в `main`. Пилот использует локальную Factory и ограничивает GitHub-проверки тестовыми runner.

Исправления пилота охватывают общий запуск панели и рабочего процесса, остановку выдачи с завершением текущих шагов, проверку Git и Docker, диагностику ответа GitHub/OpenAI и переносимость GNU timeout и транспорта Responses на POSIX. Платформа сохраняет отдельное подтверждение изменения сайта, точный SHA для сборки, проверку доверенного профиля и запрет автослияния в панели. Для тестового GitHub CI нужны runner без секретов, с `contents: read` и без разрешений на публикацию: утверждённые файлы могут исполняться тестами. Один реестр соответствует одному контуру и набору учётных данных диспетчера.

## Запуск на компьютере владельца

- **Windows.** Используйте Ubuntu в WSL2, Docker Desktop с интеграцией этой дистрибуции и Unix-сокет Docker. Держите checkout и приватное состояние в файловой системе WSL, например под `~`. Проверьте доступ к опубликованным loopback-портам из WSL. Для iPhone проксируйте порт через хост или приватную сеть с учётом режима сети WSL.
- **macOS.** Используйте Python 3.11+, Git, Docker с Compose v2 и GNU coreutils (`brew install coreutils`, нужен `gtimeout`). Разрешите Docker доступ к каталогу состояния. На Apple Silicon проверьте доступность закреплённых Docker-образов для arm64.
- **Общее.** Нужны curl для Responses, GH CLI для удалённого GitHub, Node.js для редактируемого JS и PHP CLI для редактируемого PHP. Фоновая работа зависит от питания компьютера, запущенного Docker и доступа к сети. Используйте уже доступный Docker с подходящими для владельца условиями лицензии. Скрипты systemd/SSH из STAGE-013 предназначены для отдельного Linux-хоста.

1. Создайте приватную директорию (`umask 077`, режим `0700`) вне Git. В ней сохраните `projects.json` и `accounts.json`. Начните с копии [примера реестра](../factory/orchestrator/projects.example.json), замените относительные пути на фактические. Профиль должен указывать на синтетический seed, уникальные ID и loopback-порт. Для запуска локального сайта используйте проверенный SHA из локальной ветки `base` репозитория `factory_source`. Значения для первого запуска можно сверить командами `git -C /path/to/fixture rev-parse main` и `docker compose version`.
2. Создайте хеш командой `python3 -B -m factory.control --hash-password`. Сохраните его как `{"owner":{"owner":true,"salt":"…","hash":"…"}}` в `accounts.json` под правами `0600`. Держите API и GitHub ключи в окружении процесса запуска или в менеджере секретов.
3. Из корня checkout выполните одну команду. Для проверки готовности без запуска добавьте `--check`.

```bash
python3 -B -m factory.pilot --config "$HOME/.factory-pilot/projects.json" \
  --accounts "$HOME/.factory-pilot/accounts.json" --state "$HOME/.factory-pilot/state"
```

Preflight проверяет конфигурацию, аккаунты, команды, PWA, доступ к Git, открытие SQLite и локального порта. При наличии профиля он проверяет локальный Docker, Compose, журнал и состояние контейнеров. Для уже запущенного сайта выполняется health. Для остановленного проверяется свободный порт. Для GitHub проверяются учётные данные и доступ к базовой ветке. Для Responses проверяется доступ к модели через `GET /v1/models/{model}`. Этот запрос получает метаданные модели. Диспетчер и HTTP запускаются после preflight, сообщение `Pilot ready` появляется после HTTP-ответа и heartbeat SQLite.

Откройте `http://127.0.0.1:8787`, войдите, подключите профиль и поставьте `start` с доверенным SHA. Одобрите операцию в панели, дождитесь `done`, выполните `health`. Затем создайте бизнес-задачу и проверьте историю выполнения. Второй профиль работает в той же платформе с отдельным сайтом и каталогами. Для демонстрации без WordPress и AI подготовьте свежий каталог командой `python3 -B -m factory.control.demo "$(mktemp -d)"` и передайте в launcher пути, выведенные генератором. Demo использует mock, Git и SQLite работают реально.

Ctrl-C останавливает API и выдачу новых заданий. Дождитесь завершения начатых шагов. Сайты сохраняют состояние в Docker; остановка сайта выполняется штатным `factory.py ... stop` с теми же `--site`, `--repository` и `--state <state>/wordpress`. При наличии журнала разберите его и примените штатный `rollback`, прежде чем снова запустить диспетчер. Приватный каталог и тома нужны для продолжения и восстановления.

## iPhone

Для пилота без VPS используйте существующую приватную сеть/VPN и HTTPS reverse proxy, слушающий только на её интерфейсе. Привяжите доверенное iPhone DNS-имя к хосту. Укажите точный адрес в `--origin https://panel.example.test`. Proxy передаёт исходные `Host` и `Origin` в `http://127.0.0.1:8787`. Например, Caddy может использовать `bind <private-ip>`, `tls internal` и `reverse_proxy 127.0.0.1:8787`. Установите и включите доверие к CA пилота на своём iPhone только при использовании внутреннего CA. Закройте вход с других сетей правилами хоста и проверьте отсутствие проброса с Интернета. WordPress и Docker остаются локальными.

В Safari проверьте HTTPS без ошибки сертификата, войдите, добавьте панель на экран «Домой», отправьте синтетическую задачу и проверьте статус через перезагрузку страницы. Проверьте, что доступ из сети вне пилота закрыт. WebKit iPhone в CI эмулирует браузер и viewport. Проверка DNS, proxy и установки на физический iPhone выполняется в сети владельца.

Для этого этапа выбран существующий адаптер Responses. Он сохраняет ограничения расходов и не даёт модели shell или учётных данных GitHub. После отдельного согласия на расходы настройте модель и бюджет по [STAGE-014](STAGE-014.md), загрузите проектный ключ, выполните preflight, запустите launcher и начните с одной короткой задачи отчёта по синтетическому проекту. Проверьте `done`, журнал, usage и резерв. Просроченный ключ или отказ в доступе блокирует работу с диагностикой. Таймауты, проблемы сети и временные HTTP-ошибки обрабатываются ограниченными повторами. При блокировке исправьте причину, проверьте журнал, снимите аварийную паузу и поставьте повтор. В этом этапе вызовов модели и покупок не было.

## Реальная проверка GitHub

В отдельном разрешённом репозитории с синтетическим `README.md` настройте тестовый workflow на push веток `factory/test-**` (`contents: read`, например одно задание с именем `fixture`, проверяющее наличие README). Это даёт Check Run на точном SHA ветки задачи. Выдайте токен только этому репозиторию с доступами Contents и Pull requests на запись и Checks на чтение, сохраните его в `FACTORY_GITHUB_TOKEN`. В профиле задайте `executor: "responses"`, `editable: ["README.md"]`, `github.trusted_test_ci: true`, `github.auto_merge: false` и `github.required_checks: ["fixture"]`. Используйте существующую тестовую базовую ветку.

```bash
python3 -B -m factory.tests.github_pilot --config "$HOME/.factory-pilot/projects.json" \
  --project fixture --confirm-repository OWNER/DISPOSABLE
```

Сценарий вызовет реальный Git/GitHub адаптер для создания ветки, открытия PR, повторной публикации и ожидания проверок на точном SHA. Изменение README записано самим тестом. Сценарий не вызывает модель, не выполняет слияние и оставляет тестовый PR для проверки и последующего закрытия владельцем. Проверьте ошибку с отключённой сетью и с отозванным тестовым токеном. Для полной цепочки после разрешения расходов поставьте отдельную AI-задачу из панели. После проверок и ревью PR остаётся в ожидании решения владельца. Токен и разрешённый отдельный репозиторий для удалённой записи в этой сессии отсутствовали.

## Проверки и границы пилота

На интеграционной ветке выполняются существующие `TOP-PARIKS CI` и `WordPress Factory`, включая серверный bootstrap на одноразовом runner. Локальные команды:

```bash
python3 -B -m unittest discover -s tests -v
python3 -B -m unittest discover -s factory/tests -v
python3 -B factory/tests/lifecycle.py
python3 -B factory/tests/orchestrator_lifecycle.py --wordpress
npm install --no-save --package-lock=false playwright-core@1.56.1
npx playwright-core install chromium webkit
python3 -B factory/tests/control_lifecycle.py --wordpress --browser
```

Контрольный сценарий запускает платформу через `factory.pilot`, создаёт задачу через API, проверяет очередь и Git, заводит два Docker-сайта и восстанавливает снимок. Провайдер AI в сценарии — mock. Для первого реального пилота владельцу нужны локальный хост и тестовый профиль, один разрешённый способ использования модели, отдельный GitHub-репозиторий при проверке удалённых PR и приватный маршрут с TLS к iPhone.
