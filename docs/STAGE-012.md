# STAGE-012 · WordPress Factory Core

Factory собирает тему из Git, поднимает WordPress и WooCommerce из закреплённых образов и устанавливает ZIP на отдельный экземпляр. Профили задают образы, пакеты с SHA-256, тему, синтетические данные и проверки витрины. У каждого профиля свои порт, проект Compose, тома, учётные данные БД, хранилище копий и блокировка. Образец второго профиля использует ту же тему и фикстуры. [Профиль TOP-PARIKS](../factory/sites/top-pariks.json) · [Шаблон второго сайта](../factory/sites/example-store.json) · [Проект STAGE-011](https://github.com/TonyGoalsMan1/top-pariks/pull/31)

## Локальный запуск

Нужны Linux, Python 3.11+, Git, curl, Docker и Compose v2. Для первого запуска нужен доступ к реестру образов и GitHub Releases. Выполните из корня репозитория.

```bash
release_dir="$(mktemp -d)/release"
factory() { python3 factory/factory.py --site factory/sites/top-pariks.json "$@"; }
factory build "$release_dir"
factory verify-release "$release_dir"
factory start "$release_dir"
factory health
factory backup
factory verify-backup BACKUP_ID
factory restore BACKUP_ID
factory stop
```

Подставьте ID из вывода `backup`. `stop` сохраняет тома. Магазин доступен на `http://127.0.0.1:8180`. Для второго магазина повторите команды с `factory/sites/example-store.json` и новым каталогом релиза. Для нового сайта скопируйте пример, задайте уникальный `site_id` и свободный порт, укажите каталог темы с `style.css` и `index.php`, ваш PHP-файл фикстур и маркеры маршрутов. Фикстуры должны создавать опубликованный простой товар и классическую страницу корзины. Для контейнеров используйте совместимые образы WordPress Apache и MariaDB с digest. Начальное состояние каждого сайта создаётся командой `start`. Повторный запуск сохраняет данные. Для установки обновления соберите новый релиз и вызовите `factory deploy "$release_dir"`.

## Копии и откат

- `backup` останавливает WordPress на время экспорта выделенной БД MariaDB и копирования всего тома WordPress. Манифест связывает данные с профилем и фиксирует размер и SHA-256 каждого файла. Проверенные копии хранятся в каталоге `backups` сайта под `$XDG_STATE_HOME/wordpress-factory` или `~/.local/state/wordpress-factory`. Путь можно задать через `--state` перед командой.
- `restore` проверяет профиль, хеши и структуру архива до записи. Он заменяет файлы и БД целиком, затем проверяет витрину. Для восстановления на чистых томах используйте прежний профиль и скопируйте проверенный каталог копии под тем же ID в `backups`.
- `deploy` проверяет ZIP, снимает резервную копию и записывает журнал перед заменой каталога активной темы. Если health check падает, Factory возвращает предыдущую тему и снова проверяет витрину. База и загрузки сохраняются в текущем состоянии. После подтверждённого отката команда всё равно возвращает ненулевой код кандидата. Если процесс прервали, выполните `factory rollback`: команда использует сохранённый журнал. Правила повторных попыток и критерии задач описаны в очереди. [Очередь Factory](../factory/queue.json)

## Проверки

```bash
python3 -m unittest discover -s factory/tests -v
python3 factory/tests/lifecycle.py
```

Workflow Factory запускает эти команды для PR и веток на изолированном GitHub-hosted runner. Прогон проверяет главную, каталог, карточку и добавление товара в корзину, успешную публикацию, отказ при чужой и изменённой копии, восстановление на существующих и чистых томах и откат темы после намеренно проваленной проверки главной. Проверка отката сверяет удаление файлов кандидата и сохранность изменений в БД после снимка. Два магазина запускаются одновременно. ## Границы пилота и подключение сервера

Factory рассчитана на доверенный код, синтетические данные, локальный Docker и loopback. Действующий магазин и старые workflow публикации остаются на своём контуре. Состав релиза ограничен активной темой. Обновления ядра и расширений, миграции схемы, внешний зашифрованный backup, расписание и автоматическое восстановление после принудительного завершения процесса требуют отдельной реализации. SHA-256 проверяет целостность файлов относительно доверенного манифеста. Копии STAGE-012 хранятся локально в открытом виде.

Владельцу для пилота достаточно предоставить отдельный разрешённый Linux-стенд с Docker Compose, диском для копий и ограниченным SSH-доступом. На этом хосте можно выполнить тот же прогон с синтетическими данными через loopback. Для постоянного стенда владелец должен утвердить закрытый доступ, место и сроки хранения внешних копий, порядок восстановления и отдельный профиль доступа. Реальные данные подключаются после проверки внешнего шифрования и репетиции восстановления. [План подключения из STAGE-011](https://github.com/TonyGoalsMan1/top-pariks/pull/31)
