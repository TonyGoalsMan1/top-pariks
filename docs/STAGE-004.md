# STAGE-004 · Диагностика staging FTPS

После успешного STAGE-003 подтверждены вход в аккаунт, чтение ожидаемой структуры и проверка маркера. Успешное создание маркера также подтверждает запись одного маленького файла. Для публикации дополнительно нужны чтение всего дерева темы, создание папок, запись файлов из ZIP и переносы каталогов между деревом WordPress и закрытой папкой. По старому сообщению `error_perm` точную команду и причину определить невозможно.

Строка `FTPS failed (stage=… category=… command=… reply=… error=…)` показывает этап, тип операции, FTP-команду без аргументов и числовой код. `none` означает, что соответствующего значения нет, например при проверке хешей или ошибке TLS-сертификата. Текст ответа, пути, учётные данные и имена файлов в сообщение не попадают.

| Этап и команда | Что проверить |
| --- | --- |
| `control-tls` / `AUTH`, `data-protection` / `PBSZ` или `PROT` | `500/502/504/534` могут означать, что команда или выбранный режим отклонены. Сверьте explicit TLS, сертификат и поддержку шифрованного канала данных. |
| `login` / `USER`, `PASS` или `ACCT` | `530/532` требуют проверки состояния аккаунта, учётной записи и ограничений доступа. |
| `login-directory` / `PWD` или любой листинг / `MLSD` | `500/501/502` могут означать неподдерживаемую команду или аргумент. `550` может означать неверный FTP-путь или запрет листинга. |
| `staging-marker`, `existing-theme` и этапы проверки / `RETR` | `550` может означать отсутствие файла, отсутствие доступа на чтение или блокировку файла. Сверьте точный регистр и расположение. |
| `attempt-directory`, `candidate-directory`, `candidate-upload` / `MKD` | `550/553` могут означать существующий каталог, запрет записи в родительский каталог или ограничение имени. Проверьте наличие каталога попытки, доступ на запись и квоту. |
| `candidate-upload` или `marker-initialize` / `STOR` | `550/552/553` могут означать ограничение записи, размера, типа файла или квоты. Проверьте также лимит inode и отметки провайдера об удалённых фильтром файлах, если запись прошла, но чтение или сверка затем не прошли. |
| Листинг, чтение или запись / `TYPE`, `PASV`, `EPSV` | Ошибка относится к настройке передачи или пассивного канала. Проверьте поддержку защищённого пассивного режима и доступ с GitHub Actions. |
| `backup-move`, `candidate-activate`, `recovery-*` / `RNFR` или `RNTO` | При `550/553` проверьте наличие и доступность источника, право записи в родительские каталоги, отсутствие конфликта назначения и поддержку переносов между этими деревьями на одной файловой системе. |

Код `550` объединяет несколько причин. Для подтверждения конкретного ограничения попросите InfinityFree проверить серверный журнал по времени UTC, этапу, команде и коду. [FTP Details](https://forum.infinityfree.com/t/how-to-upload-files-with-ftp/49306) · [Ограничение записи вне htdocs](https://forum.infinityfree.com/t/missing-htdocs-folder-in-hosting-account/121324)

## Проверка с iPhone

1. В Safari откройте [Client Area InfinityFree](https://dash.infinityfree.com/), затем **Accounts → Manage** у аккаунта, к которому привязан `top-pariks-test.freehosting.dev`. Если меню скрыто, в меню Safari выберите **Запросить настольный веб-сайт**. Проверьте статус аккаунта и привязанные домены. В **FTP Details** или **FTP Accounts** сверяйте сервер, порт и пользователя только в закрытой панели.
2. Из страницы аккаунта откройте **File Manager**. Проверьте, что `htdocs` относится к стенду, содержит `wp-load.php`, а в `wp-content/themes/top-pariks` есть `style.css` и `index.php`. Проверьте, что `top-pariks-backups` находится вне всех веб-корней и содержит маркер из STAGE-003. Если **File Manager** не показывает каталог, уточните его доступность через explicit FTPS или у поддержки. Видимость каталога сама по себе не подтверждает право записи.
3. Для `MKD` или `STOR` откройте **Control Panel** из страницы аккаунта и проверьте показатели диска и inode в **Statistics**. Учитывайте сохранённые попытки, полный размер кандидата и действующий лимит на отдельные файлы. Для `RNFR/RNTO` уточните у поддержки, разрешены ли переносы каталогов в обе стороны и запись в закрытую папку вне `htdocs`. Если провайдер не поддерживает закрытую папку или нужный перенос, остановитесь. Не подменяйте каталог публичным, не меняйте разрешения наугад и не удаляйте файлы при диагностике.

## Безопасный повторный запуск

1. После появления изменений в `main` для проверки без публикации откройте **Actions → TOP-PARIKS staging FTPS marker → Run workflow**. Выберите `main`, режим `check` и введите `https://top-pariks-test.freehosting.dev`. Этот режим читает структуру и маркер. Он не проверяет возможность записи или переноса.
2. Продолжайте диагностику по [STAGE-005](STAGE-005.md). При пропущенном job или любом результате без `Staging marker verified.` остановитесь.
3. Если сбой начался на `backup-move` или позже, перед любой новой публикацией проверьте сообщение `Previous theme verified after recovery.` либо вручную подтвердите состояние темы и закрытых копий по [STAGE-002B](STAGE-002B.md). При `FTPS recovery failed`, прерывании или неясном состоянии остановитесь до проверки. Копия считается проверенной после `backup-verify`, поэтому появление `FTPS backup ID` само по себе не подтверждает, что каталог `previous` создан.
4. После устранения причины, проверки состояния и отдельного разрешения на публикацию оператор может использовать ручной **TOP-PARIKS staging FTPS** с `main` и подтверждением `top-pariks-test.freehosting.dev`. Используйте новый запуск с актуальным SHA. ID образуется из номера запуска и попытки. Старые папки сохраняются, совпавший ID приводит к остановке, а GitHub сериализует workflow стенда. Убедитесь, что во время операции никто параллельно не меняет файлы через FTP или панель.

Локальные тесты без доступа к стенду выполняются командой `python3 -B -m unittest discover -s tests -v`.
