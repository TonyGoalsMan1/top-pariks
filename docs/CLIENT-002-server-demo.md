# CLIENT-002 · серверная демонстрация TOP-PARIKS

Статус — подходящий доступный сервер при бюджете $0 не подтверждён. Серверный URL для передачи заказчику пока отсутствует. Тема, ветка релиза и тег `client-001-atelier-1.3.3` сохранены. База для переноса — `9e175583a9ff7f0c2948843e716a8bc0d56b21c5`.

## Ошибка на iPhone

Владелец воспроизвёл «Could not download required files» в Safari через LTE. Документация Playground относит эту заставку к проблеме загрузки обязательного WASM или скрипта запуска. Точное имя первого неудачного запроса на iPhone неизвестно без журнала Playground или сетевой записи Safari с того сеанса. По имеющемуся сообщению нельзя установить, был ли это сетевой сбой, блокировка или другой ответ сервера. [Ограничения Playground](https://developer.wordpress.org/playground/developers/limitations/) · [Диагностика Blueprint](https://developer.wordpress.org/playground/blueprints/troubleshoot-and-debug/)

В проверенной сети HTTPS HEAD вернул 200 для оболочки Playground, опубликованного Blueprint, ZIP темы по полному SHA, WordPress 7.1.5, WooCommerce 11.3.1, обоих русских переводов и двух файлов фикстур. Эти ответы подтверждают доступность перечисленных ресурсов с точки проверки. Они не измеряют полную загрузку WASM или доступ из Safari через LTE. Перенос рендеринга и базы на сервер убирает из покупательского пути загрузку и запуск Playground.

## Перенос после подтверждения площадки

1. Выделить отдельный HTTPS-hostname и новую БД. На Linux с Docker выполнить проверку `SHA256SUMS` и восстановление через входящий в архив `restore.sh` на новом Compose-проекте и loopback-порту. Для PHP-хостинга извлечь `site-files.tar.gz`, восстановить `site.sql` в новую базу и создать отдельный `wp-config.php` с новыми секретами. Проверить лимиты на каждый файл до переноса.
2. Для нового внешнего URL сделать сериализационно корректную замену адресов через WP-CLI, проверить `home` и `siteurl`, назначить маршруты WooCommerce. Для Docker открыть публике только HTTPS через reverse proxy с сохранением host и HTTPS-схемы, оставив БД и WordPress вне публичных портов.
3. До первого внешнего открытия задать `blog_public=0`, проверять `X-Robots-Tag: noindex, nofollow`, сохранить тестовый MU-плагин из архива с блокировкой писем и только COD. Пароли экспортированных аккаунтов отключены. Учебный административный доступ предоставлять через приватный маршрут с отдельным входом. При проксировании оставить доступными штатные покупательские AJAX-маршруты и закрыть интерактивный админский вход для публики. SQL, архивы и секреты хранить вне document root.
4. В чистом внешнем сеансе проверить доверенный сертификат, отсутствие GitHub-авторизации, фильтры, вариацию, корзину, синтетический заказ без списания, запрет индексации и закрытую админку. Затем передать новый HTTPS-адрес владельцу для проверки Safari на физическом iPhone через LTE. Этот этап пока не выполнен.
