# STAGE-013 · Сервер WordPress Factory

Серверный режим расширяет [STAGE-012](STAGE-012.md) и использует его профили, проверку ZIP, снимки и smoke-тесты. Он рассчитан на отдельный Linux-хост для независимых staging-сайтов с синтетическими данными. Старые workflow и локальный Factory можно использовать по-прежнему.

## Подключение сервера и первого сайта

1. Подготовьте отдельный Ubuntu 24.04 или Debian 12/13 с systemd и доступом к репозиториям пакетов, GitHub и Docker Hub. На хосте с уже установленным Docker нужны Engine 28+ и Compose v2. Направьте DNS-запись сайта на этот хост. Откройте TCP 80 и 443 для Caddy и TCP 2222 для SSH публикации. Если есть AAAA-запись, убедитесь, что IPv6 ведёт на тот же хост. Административный SSH настраивается отдельно.
2. Создайте отдельную пару ключей Ed25519 для Actions, передайте на сервер только публичный ключ и выполните из доверенного checkout:

   ```bash
   sudo bash factory/server/bootstrap.sh /absolute/path/factory-deploy.pub
   ```

   Bootstrap устанавливает зависимости, отдельный SSH-сервис, Caddy и таймеры systemd. При повторе сохраняются ключ хоста, конфигурации сайтов, данные и сертификаты. Передайте новый публичный ключ тем же способом для ротации ключа Actions.
3. Соберите проверенный релиз и подключите сайт:

   ```bash
   release="$(mktemp -d)/release"
   profile="$PWD/factory/sites/top-pariks.json"
   python3 factory/factory.py --site "$profile" build "$release" --ref HEAD
   sudo wordpress-factory add-site "$profile" staging.example.org "$release"
   sudo wordpress-factory enable-staging top-pariks
   ```

   Caddy запрашивает сертификат ACME при первой загрузке домена и обслуживает HTTPS с перенаправлением HTTP. Дождитесь DNS и сертификата, если первый smoke завершился до их готовности, затем повторите `add-site` с теми же данными. Команда проверяет, что ID, домен и порт уникальны, и сохраняет уже созданные данные. Для второго сайта повторите сборку и `add-site` с профилем `factory/sites/example-store.json` и собственным доменом. Для нового профиля используйте имя `factory/sites/<site_id>.json`, другой свободный loopback-порт и совместимые тему и фикстуры. Храните файл фикстур под `factory/` или `sandbox/`, чтобы bootstrap установил его на сервер. Каждый профиль получает отдельный проект Compose, тома, секреты и внутреннюю сеть БД. Публичные порты обслуживает Caddy.
4. В GitHub создайте environment `factory-staging` с разрешённой веткой `main`. Добавьте secrets `FACTORY_SSH_HOST`, `FACTORY_SSH_KEY` и `FACTORY_SSH_KNOWN_HOSTS`. Последний содержит строку формата `[server.example.org]:2222 ssh-ed25519 AAAA…`. Скопируйте публичный ключ хоста и его fingerprint с доверенной серверной консоли из вывода bootstrap. Задайте для environment переменную `FACTORY_SITE_ID=top-pariks`. На уровне репозитория задайте `FACTORY_STAGING_ENABLED=true` после проверки стенда. При необходимости задайте `FACTORY_SSH_PORT` в environment, например при перенаправлении внешнего порта на 2222.

Push в `main` запускает действующий CI и Factory CI. Публикация идёт только после успешного завершения обоих и повторной проверки головы `main`. SSH-аккаунт принимает одну команду и поток из SHA коммита и ограниченного по размеру ZIP. Сервер выбирает сайт сам. Отправка shell-команд, PTY и переадресация запрещены. Один экземпляр workflow нацелен на один профиль через `enable-staging`. Остальные зарегистрированные сайты обслуживаются и копируются независимо.

## Эксплуатация и копии

| Действие | Команда |
| --- | --- |
| Проверить доступность через HTTPS | `sudo wordpress-factory monitor top-pariks` |
| Сделать зашифрованную копию | `sudo wordpress-factory backup top-pariks` |
| Восстановить локальную копию | `sudo wordpress-factory restore-copy top-pariks BACKUP_ID` |
| Восстановить внешнюю копию | `sudo wordpress-factory restore-copy top-pariks BACKUP_ID --remote` |
| Продолжить восстановление после прерывания | `sudo wordpress-factory recover top-pariks` |
| Посмотреть результаты задач | `sudo journalctl -u wordpress-factory-monitor -u wordpress-factory-backup -u wordpress-factory-queue` |
| Посмотреть события SSH-публикации | `sudo journalctl -t wordpress-factory-deploy` |

Таймер копирования запускается ежедневно в 03:00 UTC с задержкой до 15 минут. Restic шифрует локальные и внешние снимки. Политика оставляет 7 суточных, 4 недельных, 6 месячных снимков и минимум 3 последних, если они существуют. Копия включает БД, файлы и манифест STAGE-012. На время согласованного снимка WordPress останавливается, а перед передачей в S3 снова запускается. Промежуточный снимок и данные для незавершённого отката находятся в приватном каталоге в открытом виде. Используйте шифрование диска, держите место для снимков и полного восстановления. Узел очищает промежуточные копии после завершения операции или восстановления.

Для внешней копии выполните локальный `backup`, затем сохраните пароль из `/var/lib/wordpress-factory/<site_id>/restic-password` в отдельном менеджере секретов. Создайте приватный S3-bucket с блокировкой публичного доступа и выдайте ключу права чтения, записи и удаления на выделенный префикс сайта, включая list на этот префикс. Удаление нужно для retention. Через защищённый редактор создайте файл `/var/lib/wordpress-factory/<site_id>/s3.json` с правами `0600` и владельцем `root`. Формат:

```json
{
  "repository": "s3:https://s3.example.org/private-bucket/top-pariks",
  "AWS_ACCESS_KEY_ID": "<ключ>",
  "AWS_SECRET_ACCESS_KEY": "<секрет>",
  "AWS_DEFAULT_REGION": "us-east-1"
}
```

Для временного ключа добавьте `AWS_SESSION_TOKEN`. Один раз запустите `sudo wordpress-factory init-remote top-pariks`, затем `backup top-pariks` и проверьте восстановление на подготовленном изолированном стенде. Для повторного подключения существующего внешнего репозитория скопируйте сохранённый пароль и конфигурацию S3 без повторной инициализации. Для восстановления после потери узла заново подключите прежний профиль с тем же origin и подставьте ID снимка. Для просмотра доступных ID используйте журнал копирования или `restic snapshots` с тем же репозиторием и файлом пароля.

Монитор каждые две минуты проверяет WordPress, активную тему, главную, каталог, карточку товара и корзину. Если обновление провалило smoke, код возвращает прежнюю тему и проверяет её, сохраняя текущее состояние БД. Если процесс завершился между шагами, следующий монитор разбирает журнал и восстанавливает сайт. Операции на одном сайте защищены общей блокировкой Factory. Если суточный backup застал занятой сайт, он переходит в очередь. Блокировка установки защищает код и реестр при повторном bootstrap. Для уведомлений добавьте `/var/lib/wordpress-factory/<site_id>/webhook-url` с правами `0600` и HTTPS URL принимающей системы. Webhook получает JSON с `site`, `operation`, `failed` при смене состояния, включая восстановление. Для обнаружения недоступности всего хоста нужен внешний наблюдатель.

## Очередь и границы

Оркестратор может создавать задачи через `sudo wordpress-factory enqueue SITE check` и `sudo wordpress-factory enqueue SITE backup`. Таймер забирает по одной задаче из приватной очереди. Допустимые действия фиксированы. Записи остаются под ID в `/var/lib/wordpress-factory/queue`, включая состояния `.done`, `.failed` и `.interrupted`. Занятый сайт приводит к отложенному запуску. Прерванные и неудачные задачи остаются для разбирательства перед повторной подачей. У GitHub SSH нет доступа к очереди.

Обновления касаются темы. Миграции БД, обновления ядра и плагинов, высокая доступность и сценарий production требуют отдельного контура. Сайты с доступом из интернета помечены `noindex`, данные для тестовых публикаций должны оставаться синтетическими. Caddy и WordPress настраиваются для доверенного кода, поэтому ключ публикации и права изменения `main` нужно защищать как права выпуска PHP-кода в выбранный WordPress.

## Проверки

23 ноября 2026 года в изолированном Debian с Docker прошли 26 тестов FTPS, 4 теста Factory и исходный жизненный цикл STAGE-012 с двумя магазинами. Отдельная проверка через локальный HTTPS webhook доставила по одному сообщению о сбое и о восстановлении. Actionlint принял оба workflow Factory. Новый серверный прогон подтвердил изоляцию двух сайтов, успешную публикацию, откат сломанной темы, возобновление после прерывания и работу очереди. Один снимок восстановлен из локального репозитория restic и из S3-совместимого эмулятора через HTTPS.

На одноразовом Ubuntu runner прошли исходный TOP-PARIKS CI и тест системного bootstrap с Docker, уже установленным на runner. Проверены повторный запуск на развёрнутом сайте, HTTPS с внутренним CA, публикация с закреплённым ключом и отказ при попытках сменить ключ хоста, выполнить произвольную команду или открыть туннель. [TOP-PARIKS CI](https://github.com/TonyGoalsMan1/top-pariks/actions/runs/45263963680) · [Bootstrap и SSH](https://github.com/TonyGoalsMan1/top-pariks/actions/runs/45263963482/job/138005816472)

- `python3 -B -m unittest discover -s tests -v` и `python3 -B -m unittest discover -s factory/tests -v` проверяют прежние сценарии, форматы релиза, копии и очередь.
- `python3 -B factory/tests/lifecycle.py` запускает исходный жизненный цикл STAGE-012.
- `python3 -B factory/tests/server_lifecycle.py` запускает два изолированных Compose-проекта, HTTPS через внутренний CA Caddy, проверяет конфликтующие операции, публикацию, отказ и откат сломанной темы, возобновление после прерывания, зашифрованный backup, восстановление и очередь. С `FACTORY_TEST_S3=1` и установленным `moto[server]==5.1.20` дополнительно проверяет S3 API через HTTPS.
- `factory/tests/server_bootstrap.sh` предназначен для одноразового runner с systemd и sudo. Он проверяет повторный bootstrap, доступность HTTPS, публикацию через SSH, отказ при несовпадении ключа хоста и ограничения SSH. [Factory CI](../.github/workflows/factory.yml)

Реальный выделенный сервер, публичный ACME, внешний bucket и webhook владельца требуют проверки после подключения. InfinityFree, production и реальные базы данных в испытаниях не использовались.
